## 판단

보고서의 "ROS2Backend 한 줄 수정으로 단기간 완성"과 "Joint 생성만으로 적재 효과 자동 완성"은 필요한 제어·관측·실패 처리를 빠뜨린다. Pegasus 도입 가치는 있다. 적용 범위에서 검증한 비행 동역학·센서·PX4 연결을 재사용하면 P3 팀이 직접 구현할 범위를 줄일 수 있다.

## 다음 구현 순서와 소유권

1. 이번 시연은 S0/S1을 유지한다. 기존 계약·원장·접수·진행 중 stub PR을 중복 작성하지 않는다.
2. S2 착수 시 C0에 1인일을 배정해 환경·자산·PX4 연결만 조사한다. 미달이면 진단과 대안 ADR을 남긴다.
3. C1 빈 기체 → C2 지상 결합 → C3 적재 비행 → C4 수납·복구 → 병원 회랑 순서로 검증한다. 정상 결과뿐 아니라 소실·재시작·오인계 차단을 남긴다.
4. 담당별 소유권은 아래와 같다. 공용 ROS/launch 변경은 통합 담당과 계약 개정 후 진행한다.

| 담당 | 소유 범위 |
| --- | --- |
| navigation | 비행 스택과 임무 |
| simulation | 단일 World, 모의 센서, 물리 구속(constraint) |
| manipulation | 팔과 지지 전이 |
| orchestration | 승인, 물품의 현재 점유·위치(custody), 명령 전후와 복구 대조를 위한 작업 원장(journal) |

직접 제어 경로는 이미 시험한 제어기가 있거나 PX4 의존성 문제가 확인된 경우 비용을 다시 비교한다. PX4 실패를 만난 즉시 별도 controller를 작성하는 자동 fallback은 제안하지 않는다. 각 경로의 CPU/VRAM/RTF 우열도 측정 전에는 확정하지 않는다.

## 검토자가 확인할 사항

- S0 계약 §2·4의 fresh 관측 commit, §5–6의 crash/fence, §7의 취소와 새 결합·해제 계획이 충돌하지 않는가.
- `DELIVERED`와 임무 종료, 모의 GPS와 실제 실내 항법, constraint 모델과 실제 래치 성능이 분리되어 있는가.
- 1인일 상한이 C0에만 적용되고 비행·기구 전체 일정의 약속으로 읽히지 않는가.
- C2/C4의 적용/관측/원장 경계에서 잘못된 body·중복 constraint·결과 유실을 시험할 수 있는가.
- 기존 T01–T44가 보존되고 PG-T01–PG-T07이 미실행 하위 명세로 표시되어 있는가.

이번 변경은 계획 문서와 검토 기록이다. 실행 코드·의존성·인터페이스·launch·스텁·계약 본문은 바꾸지 않는다. 저장소 검증 명령과 결과는 이 변경 PR에 기록하며, ROS L2와 Isaac/PX4 L3는 미실행이다.

## PR #364 후속 보완

머지 전 자체 검토의 두 P2를 계획에 반영했다. 사용자는 해결안을 검토하고 반영 진행을 요청했다. 이는 S2 실행·현장 검증 완료나 새 헤드의 독립 리뷰 승인을 의미하지 않는다.

- §17.5: 접촉식/FixedJoint식 그립을 분리했다. 포크 독립 지지 하에 구속을 교체하고 동시 FixedJoint step을 금지한다. 실패 시 진행 차단·실제 상태 대조를 명시했다.
- §13.8: 원본 명령의 generation·sequence·시각·유효기간과 별도 감시를 정의했다. 재전송은 만료를 연장하지 않으며 clock domain 대응, 만료 대응, 재개 조건을 검증한다.
- PG-T04/05: 생성기만 정지하는 시험과 구속 교체의 세 실패 사례를 추가했다. 수치 합격선은 미설정 상태이며 pilot/acceptance 전에 정한다.
- 가독성 의견 1–4는 기술 조건을 보존해 수정 채택했다. 의견 5의 “비행 단계만”은 실제 변경 범위를 축소하므로 채택하지 않고 비행·Pod 인계·검증을 포함해 요약했다.
- 후속 통합 기준 main은 `95bb05680d866124b05fc3849352d4b0540a9e27`이다. 최초 검토의 #358 OPEN 기록은 당시 관측이며 이 기준에서는 병합되어 있다.

이번 보완도 문서 변경이다. S0 계약 §2·4의 관측 기반 commit, §5–6의 crash/fence, §7의 취소 경계를 유지한다. 비행 어댑터 generation은 후속 S2 요구이며 S0 상태 전이를 구현한 것으로 세지 않는다. 검증 명령·결과와 새 헤드 SHA는 PR 댓글에 기록한다.
