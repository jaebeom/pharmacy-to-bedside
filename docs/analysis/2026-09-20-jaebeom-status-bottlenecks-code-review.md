### P1 — UR5 selfdemo의 실패가 다음 단계와 칸 계수로 전파됨(P32)

현재 코드에서 다음을 확인했다.

- `sim/standalone/p3sim/ur5_cell.py`, `Ur5Cell.suck`: 거리 초과 시 miss 로그를 남기고 holding을 만들지 않는다.
- `sim/standalone/pharmacy_stage.py`, `ur5_update`: phase 시작의 suck 뒤 holding 확인 없이 진행한다. TCP TIMEOUT도 로그 뒤 `seq.phase_done()`으로 다음 단계로 간다.
- 같은 파일 `finish_ur5_pick`: `in_slot=False`여도 slot을 증가시키고, 끝에서는 carried를 park/release한 뒤 slot을 0으로 돌린다. 실제 적재 수를 근거로 full을 판정하는 흐름이 아니다.
- `selfdemo_update`보다 먼저 `ur5_update`가 실행되며 `--loop`는 배출 수만 제한한다. 벨트에 남은 실패 봉투의 재시도 상한이 되지 않는다.

실습12의 P32와 일치한다. **이 경로는 selfdemo다. ROS arm_node가 동일한 방식으로 실패한다는 주장으로 확장하지 않는다.** ROS 쪽에는 별도의 gripper/placement opt-in 경로가 있고 결합 검증이 남아 있다.

**수정 순서 제안:** ①TIMEOUT·holding 실패에서 단계 중단 ②실제 안착 확인 뒤에만 칸 확정 ③만재/잔류 물품 상태를 명시적으로 종료 ④시도 상한·실패 종결·리셋 복구. 실패를 성공으로 세지 않는 판정을 먼저 고치고 P31의 IK 자세·기하를 반복 측정한다.

완료: miss·TIMEOUT·칸 밖·만재를 주입했을 때 다음 배출/적재가 차단되고 실패 이유가 남는다. 그 뒤 빈 칸부터 만재까지와 리셋 후 재실행을 확인한다. 접촉을 감추거나 거리 허용치를 넓혀 성공률을 만들지 않는다.

### P1 — “가상 attach 안착”과 물리 파지·ROS 통합의 완료 기준

`Ur5Cell.follow()`는 `set_world_pose()`로 봉투를 매 update TCP에 따라 이동시키고 속도를 0으로 만든다. `suck_nearest()` 주석도 virtual attach이며 physical grasp로 세지 않는다고 명시한다.

따라서 12l의 5/5는 **가상 attach 모델에서 관측한 5칸 안착**이다. 접근 기하·도달·위치 검증에는 유효하다. 흡착력·접촉·하중 유지의 증거 또는 ROS 팔의 성공률은 아니다. #239의 “진짜 흡착” 표현은 이 모델 범위로 한정해야 한다.

**보완:** 다음 acceptance 범위 결정에 attach 모델을 명시한다. 가상 모델을 채택하면 시연·지표에도 그대로 표시한다. 물리 흡착을 목표로 유지하면 그리퍼 모델·하중·해제·낙하 검증을 별도 선행 작업으로 둔다. ROS 결합 L3는 `mode=ros`, 실제 arm·detector와 opt-in 짝을 지정해서 별도로 닫는다.

### P1 — 목적지가 틀려도 SUCCESS가 되는 판정기(INT-3)

`src/rokey_p3_orchestrator/.../run_log.py`의 OrderLedger는 요청했던 주문인지 확인하지만 **기대 보관함을 저장·대조하지 않는다**. `present=True`인 임의 보관함 관측이 있으면 `judge()`가 SUCCESS를 반환한다. 정적 의심에 그치지 않고 현재 소스로 재현했다.

```python
from rokey_p3_orchestrator.run_log import OrderLedger
ledger = OrderLedger()
ledger.note_status('ord-0001', 'DELIVERED', request_id='repro-wrong-destination')
ledger.note_observation('ord-0001', 'bed_b2/cabinet', True)
print(ledger.records()[0]['state'])  # SUCCESS
```

기대 목적지를 넘길 API 자체가 없으므로 예시는 의도적으로 잘못된 보관함을 주입한 것이다. 주문 풀의 ord-0001 목적지는 bed_a1이다. 실제 오배송이 발생했다는 증거는 아니다.

**보완:** 요청 수락 시 확정한 실제 목적지를 기대값의 출처로 정한다. 웹이 목적지를 정규화·변경할 수 있어 주문 풀만 다시 읽으면 안 된다. request/order/epoch와 기대 cabinet을 결합하고, 불일치·기대값 누락·이전 세대 관측은 성공으로 올리지 않는다. 정상 일치·불일치·미확인·리셋 후 지연 관측 시험을 붙인다.

새 판정은 새 protocol·실행에 적용하고 기존 frozen pilot과 run은 고치지 않는다. 조제실 HOLD_RETURN pilot은 cabinet을 쓰지 않으므로 현재 3건을 이 결함 때문에 실패로 재분류하지 않는다.

### P1 — 관측이 발행되는 것과 동작을 차단하는 것은 별도

실습15b는 BeltObservation 전달과 전이를 확인했다. 봉투 소실·속도 미수신을 주입한 fail-closed 판정이나 전체 guard 결합을 확인한 시험은 아니다. [계약 구현표](../architecture/delivery-contract-v1-status.md)는 아직 모든 신규 토픽을 L3 미실행이라고 적어 일부 낡았다.

**보완:** BeltObservation → command_seq/GripperState → ArmClearance → placement_check → orchestrator guard를 기존 런카드 순서로 연결한다. 기하값·관측 자세·시한은 실측 후 채운다. 각 단계에서 stale/UNKNOWN/epoch 불일치를 주입하고 다음 동작 차단을 본다. N09를 안착 소비와 함께 해결한다. DockingState는 발행 구현만 있으며 소비자가 없는 점도 F3 인계에 포함한다.

### P1 — 증거 원본과 acceptance 정의의 공백
