### 말로 밝힐 것

- 1부: 조제실 구간만 돈다. 주문은 침상에 가지 않고 복귀한다(`HOLD_RETURN` 이 정상이다).

- STAT: 전부 스텁이고 본선과 연결돼 있지 않다.

## 2. 띄우기와 내리기

정본은 `tools/demo_v2.sh` 다(#216). 쓰는 법과 환경 변수는 [tools README](../../tools/README.md) 의 "시연 한 명령" 절과 스크립트 머리 주석에 있다. 9/18 [실습9](../practice/practice-09.md) 리허설이 이것으로 처음 끝까지 돌았다(`up` 20:06:31 → 스택·웹 20:07:50).

```bash
tools/demo_v2.sh env      # 쓰일 값(P3_DOMAIN·P3_M0609·P3_DISPENSER_FILE 은 필수)
tools/demo_v2.sh cmds     # up 이 칠 명령을 띄우지 않고 본다
tools/demo_v2.sh up       # 기동 전 확인 → stage(PLAY) → arm(캐시 16/16) → stack → web → 브라우저
tools/demo_v2.sh status   # 트리 sha·기동 시각, 세션마다 떠 있는지와 주요 줄
tools/demo_v2.sh down     # browser·cap·web·stack·arm → stage 에 C-c, exit 코드
```

- 남의 Isaac 이 떠 있으면 멈추고 출력만 한다. 세션 이름은 `p3v2-stage`·`-arm`·`-stack`·`-web`·`-cap`·`-browser` 다(`P3_SESSION_PREFIX`).

### 본 시연 직전에 할 것 (보충 실패 P30, 재범 결정 34)

보충 실패의 코드 수정은 시연 뒤다. 시연은 운영으로 막는다. 스테이지의 `--hold-distance` 는 완화하지 않는다.

1. **m0609_arm 과 스테이지를 새로 띄운다.** 선반 칸 고르기 순서는 팔 노드가 뜰 때 정해지고 리셋으로는 초기화되지 않는다. 리허설을 이어서 돌리면 같은 칸을 다시 쓰는 구간에서 시연을 시작하게 된다.
   - 새로 띄우면 **처음 5회는 서로 다른 칸**이다. 같은 약을 연달아 보충하면 6번째에 같은 칸이 다시 나온다. 원통·모듈이 번갈아 오면 7번째다.
   - 가정은 `v2_seed` 7, 시험 장면 16칸이다. 원통 8칸과 모듈 8칸은 별도 목록이고 보충 한 번에 한 칸을 뽑는다.
   - "몇 번째"는 goal 수 기준이다. 실패·재시도가 끼면 한 칸씩 밀린다. 시연 대본은 보충 3–4회라 어느 가정에서도 재사용 구간에 닿지 않는다.
   - 관측(실습19): 같은 기동에서 리허설 + 본 회차로 보충 4회를 돌렸고 **선반 칸이 겹치지 않았다**(`upper_right/r0c1`·`floor_left/r1c0` → `upper_right/r1c0`·`floor_left/r0c0`). 팔 노드를 새로 띄운 2부는 리허설과 같은 칸 순서였다.
2. **호스트의 자원 샘플러와 폴링(`curl` 반복)을 모두 끈다.** 관측이 필요하면 **1분 샘플러 하나만** 남긴다. 기동 스크립트는 샘플러를 띄우지 않는다.
   - 실습19 에서 둘이 겹쳤다. 기동 구간(약 90 s) 동안 하루 종일 도는 1분 샘플러와 기동 스크립트의 `sample.sh` 가 같이 돌았다.
   - 실습13 의 보충 실패 때 1분 부하(load1)가 3.75–9.8 이었다. 새벽 실행보다 높다. 원인으로 확정된 것은 아니다.
3. **팔은 약통의 실제 자세를 보지 않는다.** 보충 계획은 재고 JSON 의 명목 집 자리(`canister_home`)로 세운다.
   - 약통이 그 자리에서 벗어나 있거나 잡는 순간 밀리면 파지 판정 거리(`limit 0.08`)를 넘긴다. 그때 로그는 `Refill …: 실패. grasp: holding 이 2.0 s 안에 true 가 되지 않았다` 다.
4. **보충이 2회 연속 실패하면 리셋한다.** 한 번 실패는 orchestrator 가 5 s 뒤 다시 보내고 최대 3회까지 시도한다. 재시도는 같은 약이라 같은 8칸에서 다시 뽑는다. 같은 칸이 다시 나올 확률은 1/8 이다. 두 번 연속이면 스테이지 상태를 의심하고 리셋으로 약통을 제자리로 되돌린다.
   - 보충이 실패해도 orchestrator 는 죽지 않는다(#342). 그 전에는 죽었다(9/20 실습13, #240).
   - **3/3 으로 굳어도 리셋 한 번이면 회복된다**(실습20 C 관측). 리셋으로도 안 되면 `down` → `up`(약 2분)이고, 그 시간이 없으면 대체 영상으로 넘어간다.
5. **회차에 `P3_ARM_CMD` 같은 덮어쓰기 변수를 썼다면, 시연 전에 `tools/demo_v2.sh cmds` 로 팔 줄이 기본과 같은지 본다.** 파일 전체를 해시로 비교하지 않는다 — `--kit-log-file` 경로가 회차마다 달라 늘 다르게 나온다.

### 보충 뒤 낙하 확인 (#397)

보충마다 `released` 뒤에 그 통이 바닥에 닿았는지 본다. 스테이지 로그에서 그 통 프림의 `GroundPlane` `touch`(`a=` 가 통 프림)를 찾는다. 있으면 통이 칸에 들어가지 않고 떨어진 것이다.

### 녹화와 캡처 (재범 규칙, 9/20)

**창 모드로 돌리면 녹화를 켜고 시작한다. 대본 단계마다 캡처를 남긴다.**

1. `up` **전에** 주기 캡처를 켠다: `export P3_CAPTURE_EVERY=10`(초). 기본은 꺼짐이고 환경 변수로만 켜진다. `P3_CAPTURE_WINDOW` 에 창 이름 일부를 주면 그 창만 찍는다. 파일은 `$P3_LOG_DIR/<stamp>-shots/` 에 쌓인다.
   - 도구가 없거나 `DISPLAY` 가 없으면 스크립트가 캡처를 스스로 끄고 그 줄을 남긴다. 그때는 아래 "못 했으면" 규칙을 따른다.
2. 화면 녹화는 따로 시작한다. `master01` 은 ffmpeg `x11grab`(GStreamer 에 `h264parse` 가 없다), `master02` 는 `gst-launch-1.0 ximagesrc` 다.
3. 대본에서 **일곱 장**을 남긴다: 기동 직후(연결됨·SIM 시간), 자동 긴급 트립 카드, 1인 요청 대화창, 조제기 패널의 `PAUSED` 가 사라진 순간, 묶음 요청 대화창(`bed_b1` 입력과 주황 경고), 묶음 트립의 `DOCKED`, 리셋 뒤 비워진 이벤트·알람.
4. **녹화가 화면을 찍고 있는지는 크기가 아니라 화면 캡처 한 장으로 본다.** 녹화 중인 mp4 는 프레임을 열 수 없고, 잠금 화면만 찍힌 녹화도 크기는 0 이 아니다.
5. **한 파일로 길게 찍지 않는다. 로봇이 움직일 때만 바퀴별로 나눠 찍는다**(재범 지시, 9/21).
6. 끝나면 파일 이름·크기·sha256 을 실습 문서에 적는다. 원본은 깃에 올리지 않는다.

**못 했으면:** headless 라서 녹화·캡처가 불가능하면 그 이유를 실습 문서에 한 줄 적고 대체 증거(스택·스테이지 로그, 토픽 echo, 집계 출력)를 남긴다. **"없음"만 적고 닫지 않는다.**

- 볼 신호의 근거(코드):
  - `PAUSED` 는 조제기 상태의 `paused_item_ids` 가 비면 사라진다. 그 순간 orchestrator 가 `DISPENSER_RESUMED` 를 낸다(`dispenser_inventory.py` `refill`).
  - `보충 중` 은 `REFILL_REQUESTED` 뒤 `REFILL_DONE` 이 오면 사라진다(`web/backend/app/state.py` `_refilling`). `REFILL_DONE` 은 `DISPENSER_RESUMED` 보다 먼저 온다. 그래서 `PAUSED` 가 사라진 것을 기준으로 본다.
  - 웹의 409 검사(`alarms.py` `unavailable_items`)도 `paused_item_ids` 와 슬롯 수량을 본다.
- 소요 가늠(실습8, sim s): 보충 한 번 46.4-52.4 s, 재개까지 7.5-9.4 s 더(아래 소요 표). 1인과 묶음의 한 바퀴는 아직 재지 않았다.

- `single`·`urgent` 는 주문이 정확히 1건이어야 한다. 웹 백엔드가 먼저 400 `bad_mode_for_orders` 로 막는다(`web/backend/app/main.py`). 오케스트레이터도 정거장을 만들지 않고 거부한다(`trip_fsm.py` `_build_stops`). 실습8 의 묶음 409 두 번은 주문 3건을 `mode` 0 으로 보낸 요청 실수였다.
- `batch_room` 은 주문마다 환자의 침대가 있어야 하고, 침대마다 정거장 하나가 된다.
  - **오케스트레이터**는 묶음에서 `destination_id` 를 쓰지 않는다(`trip_fsm.py` `_build_stops`).
  - **웹 화면과 웹 백엔드는 모양이 맞는 값을 요구한다.** 비면 화면이 `destination_id 을(를) 채워야 합니다` 로 막고 서버로 보내지 않는다(`web/frontend/js/main.js`). 백엔드도 비면 409 `bad_destination` 이다.
  - 묶음에서는 **`bed_b1` 을 직접 넣는다.** 화면이 자동으로 채우지 못한다.
    - `ord-0003`(bed_b1)과 `ord-0004`(bed_b2)의 침상이 갈리기 때문이다(`autofillDestination` 은 침상이 하나로 모일 때만 채운다). 9/20 새벽은 curl 에 `bed_b1` 을 넣어 통과했다.
    - 빈 칸 아래에 주황 안내가 이미 뜬다: `고른 주문들의 침상이 갈립니다 — 묶음 목적지를 직접 정하세요`.
    - `bed_b1` 을 넣으면 안내가 주황 경고로 바뀐다: `후보 목록에 없는 목적지입니다 — 수락은 되지만 실물에서 GoToZone 이 거부해 HOLD_RETURN 으로 끝날 수 있습니다`. **정상이다.** 후보 목록(`GET /api/destinations`)은 `zones.yaml` 을 읽어 `bed_a1`·`station_a` 둘뿐이고, 이번 시연은 병동에 가지 않는다.
    - 대화창을 취소했다 다시 열면 이 값이 지워진다. 다시 넣는다.
  - 1인 `ord-0001` 은 침상이 하나라 `bed_a1` 이 자동으로 들어온다.
- **묶음은 품목이 겹치지 않게 보낸다.** 위 대본 표의 묶음 `ord-0003`(amox) + `ord-0004`(ibu)가 이 규칙을 따른다. 아니면 재고를 확인한 뒤 보낸다. 실습9 에서 amox 2건이 든 묶음은 재고 1 이라 한 건이 `ABORT out_of_stock` 으로 끝나고 error 알람이 남았다([실습9](../practice/practice-09.md) P23). 웹의 보내기 전 `insufficient_stock` 검사는 이제 **`main` 에 있다**(`1a03db4`). 묶음이 재고를 넘기면 보내기 전에 409 로 막고 모자란 품목을 말한다.
- 재고 파일이 slot a 1 이라 약품마다 첫 조제 뒤 보충(재고 소진 → 레일 M0609 → 재개)이 나온다.
- **보충 중에는 그 약품을 요청하지 않는다.** 웹이 409 `refill_in_progress`("보충 중 — 재개 뒤 다시 (약품)")로 먼저 막는다(재범 결정 "보충 중에는 웹에서 미리 거부", `web/backend/app/main.py`). 이 선검사가 없던 실습8 에서는 보충 중 1인 요청이 `ABORT out_of_stock` 으로 끝났다([ADR 0001](../adr/0001-orchestrator-trip-fsm.md) 실패 행, 설계대로). 이벤트 이름이 `ORDER_DONE` 이라 성공처럼 보이니 `orders.jsonl` 의 claim 을 본다(master02).
- **묶음 도중에는 보충이 나오지 않는다(계산).** 시연 재고 파일은 슬롯 a 1·b 0, 임계 1 이고 보충 캐니스터는 5개들이다(`config/dispenser.yaml` 의 `shelf`). 대본대로면 1인·자동 요청이 각 약품의 마지막 한 봉투를 쓰고 보충으로 5 가 들어온다. 묶음의 두 주문은 거기서 하나씩 빼 4 가 남아 임계 1 에 닿지 않는다. 9/20 실행도 그랬다(#240).
- 그래도 겹치면 이렇게 된다(현행 동작, `test_batch_refill_overlap.py`·`test_batch_refill_block.py`).
  - 보충이 도는 중에 묶음을 넣으면 웹이 409 `refill_in_progress` 로 막고, 막은 품목과 주문 ID 를 응답에 넣는다. 묶음의 **한 주문만** 막혀도 요청 전체가 거부된다.
  - 묶음 도중에 임계에 닿으면 `REFILL_REQUESTED` 만 나가고 배출은 이어진다. 트립은 보충을 기다리지 않는다.
  - 재고가 0 인 주문은 그 주문만 `ABORT out_of_stock` 이고, 같은 트립의 나머지는 그대로 간다.
- **리셋은 보충이 끝나고(`dispenser.refilling == false`) 트립이 없을 때(`trip == null`)만 누른다.** 실습8 에서 보충 중 리셋은 그 보충을 버렸다(`refill 결과를 버린다. epoch 1 != 2`, 팔 `취소됨`).

### 거부 코드로 무엇을 기다릴지 안다 (실습13 관측)

거부는 빨간 문구의 `code` 로 읽는다. 문구가 아니라 `code` 로 판단한다.

| `code` | 뜻 | 할 일 |
| --- | --- | --- |
| `barrier_running` | 리셋 직후다. `detail.accept_in_s` 에 남은 시간이 있다 | 약 3.5 s 기다린다. 그 뒤 **자동 긴급이 트립 카드에 뜬 것을 보고** 넣는다 |
| `trip_in_progress` | 트립이 도는 중이다 | 트립 카드가 "대기 중"이 될 때까지 기다린다 |
| `refill_in_progress` | 그 약품이 보충 중이다. `detail` 에 `item_id`·`order_id` 가 있다 | 조제기 패널의 `PAUSED` 가 사라질 때까지 기다린다 |
| `unknown_or_used_order` | 이 epoch 에서 이미 쓴 주문이다(예: `이미 쓰인 order_id: ord-0001`) | `used=false` 인 다른 주문을 고른다 |

- **`DISPENSER_RESUMED` 가 나온 뒤에도 잠깐 더 거부된다.** 실습13 에서 이벤트가 나온 뒤 약 8 초 동안 snapshot 의 `paused` 에 품목이 남아 409 `refill_in_progress` 가 한 번 더 났고, `paused` 가 빈 뒤에 200 이었다.
  - 그래서 기준은 **이벤트가 아니라 화면의 `PAUSED` 딱지**다. 지금 대본의 기준이 관측으로 확인됐다.
  - 8 초의 원인은 **미확인**이다. 조제기 상태는 1 Hz 로 나가고(`orchestrator_node._publish_dispenser`), `paused_item_ids` 는 `DISPENSER_RESUMED` 를 내는 같은 호출에서 비워진다(`dispenser_inventory.refill`). 그래서 발행 주기로는 설명되지 않는다. 다른 약품이 아직 보충 중이었을 가능성을 포함해 조사 중이었다.
- **`refill_in_progress` 와 `trip_in_progress` 의 순서는 코드와 관측을 더 맞춰 봐야 한다.** 코드(`web/backend/app/main.py`)는 보충 검사(7.5)를 트립 검사(8)보다 먼저 한다. 실습13 관측은 트립이 도는 중에 `trip_in_progress` 가 먼저 나왔다는 것이다. 그 요청의 품목이 그 시점에 막혀 있지 않았다면 둘은 어긋나지 않는다. **확인 중이다.** 발표자는 어느 쪽이든 문구의 `code` 대로 기다리면 된다.

### 화면에서 넣는 법 (프론트 점검 WEB-3, 코드 재확인)

- 요청 payload 의 필드는 `order_ids` 가 아니라 `orders`(객체 배열, 계약 7.2)다. `request_id` 는 화면이 `web-<epoch>-<HHMMSS>` 로 만든다.
- 모드 선택지는 고른 건수에 따라 바뀐다. 1건이면 `0·1인`·`1·긴급`, 2건 이상이면 `2·병실 묶음`·`3·병동 묶음` 이다.
- 보내기와 리셋은 **브라우저 confirm 창**이 먼저 뜬다. 확인을 눌러야 나간다.
- 쓴 주문은 체크박스가 잠긴다(`사용됨` 딱지). 그래서 화면에서 `ord-0002` 를 눌러 409 를 보이는 장면은 만들 수 없다.
  - 주문 목록은 **대화창을 열 때마다** 새로 받는다. 리셋 뒤에는 대화창을 다시 열어야 `used` 가 갱신된다.
- 보충 중에 보내면 화면 문구는 `<약품> 보충이 끝나면 다시 눌러 주세요` 다(서버 409 `refill_in_progress` 의 `detail.item_id`).
- 리셋하면 이벤트·알람은 epoch 이 바뀌는 순간 비워진다.
- **`?demo=1`(시연 모드)은 인터락 신호 표·이벤트 타임라인·에러 로그 탭·단계 스텝퍼를 감춘다**(`css` 의 `body.is-demo`). 글자는 커진다(현재 단계 48 px).
  - `tools/demo_v2.sh` 의 `P3_WEB_QUERY` 기본값이 `?demo=1` 이다. 그대로 띄우면 타임라인이 보이지 않는다.
  - 대본의 "타임라인에서 배출 → 벨트 → 픽 → 적재 확인"을 하려면 `P3_WEB_QUERY=` (빈 값)로 띄우거나 주소에서 `?demo=1` 을 지운다.
  - 어느 모드로 시연할지는 **미정(재범)** 이다. 9/20 새벽 실행은 웹 요청을 curl 로 보내 화면 모드와 무관했다.

### curl 로 넣을 때 (터미널에서 대신 넣는 경우)

화면 대신 터미널에서 요청을 넣을 때 쓰는 본문이다. 아래는 **실습19 에서 실제로 보낸 것**이다.

```bash
# 1인
curl -s -X POST http://127.0.0.1:8000/api/requests -H 'Content-Type: application/json' \
  -d '{"request_id":"p19-single","mode":0,"destination_id":"bed_a1",
       "orders":[{"order_id":"ord-0001","patient_id":"1001","item_id":"drug-amox"}]}'

# 묶음 — 목적지는 직접 넣는다(화면과 같다)
curl -s -X POST http://127.0.0.1:8000/api/requests -H 'Content-Type: application/json' \
  -d '{"request_id":"p19-batch","mode":2,"destination_id":"bed_b1",
       "orders":[{"order_id":"ord-0003","patient_id":"1003","item_id":"drug-amox"},
                 {"order_id":"ord-0004","patient_id":"1004","item_id":"drug-ibu"}]}'

# 리셋 — 빈 본문. 202 가 돌아온다(끝났다는 뜻이 아니다)
curl -s -X POST http://127.0.0.1:8000/api/reset -H 'Content-Type: application/json' -d '{}'
```

- `request_id` 는 회차마다 새 값을 쓴다. 같은 값을 다시 보내면 409 `duplicate_request_id` 다.
- **`order_id` 만 보내도 된다.** 서버가 주문 풀에서 `patient_id`·`item_id` 를 채우고, 1인은 `destination_id` 를 비워도 풀의 침상으로 채운다(응답의 `destination_source: "order_pool"`). 다만 **그 짧은 형태는 Isaac 에서 돌려 본 적이 없다**(코드 확인, L3 미실행). 당일에는 위 형태를 쓴다.
- 사람이 화면으로 넣는 절차는 [화면 버튼 리허설](demo-rehearsal-buttons.md)이 정본이다.

### 발표자 점검표

프론트 점검(WEB-3)의 10줄이다. 위 대본 표와 같은 순서다.

1. 웹 화면을 띄운다. 타임라인을 볼 것이면 `?demo=1` 없이 띄운다(위 항목).
2. 상단이 "연결됨"(초록)이고 SIM 시간이 흐르는지 본다. 멈춰 있으면 시작하지 않는다.
3. 자동 긴급 `ord-0002` 가 스스로 나간다. 트립 카드에 뜨면 정상이다. **리셋 뒤에도 이것이 트립 카드에 뜬 것을 보고 나서 웹 요청을 넣는다.**
4. 그 트립이 끝날 때까지 기다린다. 트립 카드가 "대기 중"으로 비면 다음이다.
5. [요청 넣기] → `ord-0001` 체크 → 모드 `0·1인` → 목적지에 `bed_a1` 이 자동으로 들어온다 → 보내기 → confirm 확인.
6. 트립이 끝나 "대기 중"이 되면 조제기 패널을 본다.
7. 패널 머리의 `PAUSED`·`보충 중` 이 **둘 다** 사라지고 보충 줄이 없어질 때까지 기다린다. 남아 있으면 묶음이 409 로 거부된다.
8. [요청 넣기] → `ord-0003`+`ord-0004` 체크 → 모드 `2·병실 묶음` → **목적지 칸이 비어 있다. `bed_b1` 을 직접 입력한다.** 주황색 `후보 목록에 없는 목적지입니다` 경고가 뜨는데 정상이다. 이번 시연은 병동에 가지 않는다.
9. 보내기 → confirm 확인. 거부되면 빨간 문구의 `code` 를 읽는다. 무엇을 기다려야 하는지가 적혀 있다.
10. 리셋은 보충이 끝나고 트립이 없을 때만 누른다. confirm 뒤 이벤트·알람이 비워지면 완료다.

### 자동 요청(order_generator)과 쓴 주문

**스택은 웹 요청과 별개로 epoch 마다 요청 1건을 스스로 보낸다.** 웹에서 넣기 전에 이것을 먼저 안다.

- 누가: `stub_loop.launch.py` 가 `order_generator` 를 늘 띄운다.
- 몇 건: launch 기본 `max_requests` 는 `1` 이다. `tools/demo_v2.sh` 는 이 값을 바꾸지 않는다.
- 언제:
  - 기동 뒤 `start_delay_s`(3.0 s, 벽시계) 가 지나면 보낸다.
  - 리셋마다 새 epoch 의 `RESET_DONE` 을 보고 `reset_settle_s`(3.5 s, 벽시계) 뒤에 다시 1건을 보낸다.
  - 근거: `order_generator_node.py`, `request_pacer.py`.
- 무엇을:
  - 주문 풀(`P3_ORDER_POOL`, 기본 `src/rokey_p3_orchestrator/config/order_pool.yaml`)의 주문 하나가 요청 하나다. 긴급이 큐 맨 앞에 선다(`order_pool.py` `build_requests`·`RequestQueue`).
  - 기본 풀에서는 **`ord-0002`(`drug-ibu`, `bed_a2`, 긴급)** 다.
- 쓴 주문:
  - 같은 epoch 안에서 이미 쓴 `order_id` 는 다시 받지 않는다.
  - 웹은 409 `unknown_or_used_order` 다(`web/backend/app/main.py`).
  - orchestrator 는 goal 을 거부한다(`orchestrator_node.py` 사용 표).
  - 자동 요청이 수락되면 그 주문도 쓴 것으로 친다(`web/backend/app/state.py` 의 `REQUEST_ACCEPTED`).
  - 두 사용 표는 `RESET_DONE` 에서 비워진다.
- **리셋 직후에는 `ord-0002` 도 잠깐 넣을 수 있다.** `RESET_DONE` 에서 사용 표가 비고, 웹은 그 3.5 s 뒤부터 다시 받는다. 자동 요청도 같은 3.5 s 뒤에 나간다. 그래서 그 순간에 넣으면 웹이 대본 1 의 주문을 먼저 가져간다(백엔드 점검 WEB-2, #331). 자동 긴급이 트립 카드에 뜬 것을 보고 넣는다.
- 그 뒤에 웹에서 `ord-0002` 를 넣으면 409 `unknown_or_used_order` 가 난다. 웹 화면의 주문 목록에서 `used=false` 인 것(기본 풀이면 `ord-0001`·`ord-0003`·`ord-0004`)을 고른다.
  - 관측(9/20 L3-1 1회차, master01, 트리 `419b20b`, #240):
    - 자동 요청이 epoch 마다 `ord-0002` 긴급을 보냈다(`r001-0001`·`r002-0001`).
    - epoch 1 웹 `ord-0001`·`ord-0004` 는 통과했다.
    - 리셋 뒤 웹 `ord-0002` 는 409 로 거부됐다.
- 자동 요청을 끄는 launch 인자는 **없다.** `max_requests:=0` 은 끄는 값이 아니라 "풀 전부"다(launch 인자 설명). 끄려면 launch·제품 코드를 바꿔야 해서 이 runbook 범위 밖이다(시연 보호).
- 자동 요청과 웹 요청이 겹치면(웹 트립이 도는 중에 자동 요청이 나가면):
  - orchestrator 가 거부하고, generator 는 그 요청을 큐에서 빼고 다음 요청으로 넘어간다(`_on_goal_response`·`_release`). 그 주문은 쓴 것이 되지 않는다.
  - 이것은 코드에서 읽은 것이고 시연 장면에서는 관측하지 않았다(미확인).
- 대본 1(긴급)은 이 자동 요청이다(위 결정).
- **한 epoch 에서 대본을 끝까지 돌리려면 자동 요청을 대본 1 로 친다.** 웹은 1인 1건 + 묶음 2건이다: 1인 `ord-0001`, 묶음 `ord-0003`+`ord-0004`.
  - 기본 풀은 4건이다(`ord-0001`·`ord-0003` = amox, `ord-0002`·`ord-0004` = ibu). 자동 요청이 `ord-0002` 를 쓰면 웹에 3건이 남는다.
  - 웹으로 긴급까지 넣으면 묶음에 쓸 주문이 1건밖에 안 남는다.
  - 같은 약품의 두 번째 주문은 보충이 끝나고 재개된 뒤에만 받는다(409 `refill_in_progress`). 자동 요청 `ord-0002`(ibu) 뒤의 `ord-0004`(ibu), 1인 `ord-0001`(amox) 뒤의 `ord-0003`(amox)가 그 경우다.
- 묶음 요청에서 검사하지 않는 것(코드 확인):
  - 같은 병실인지 보지 않는다(`trip_fsm.py` `_build_stops` 는 주문마다 침대를 찾을 뿐이고, 웹도 보지 않는다). `ord-0003`+`ord-0004`(bed_b1·bed_b2)도, bed_a1 을 섞은 조합도 거부되지 않는다.
  - `pharmacy_only` 에서는 정거장에 가지 않는다.
  - 웹과 orchestrator 는 요청의 `mode` 를 쓴다. 주문 풀의 `mode` 와 비교하지 않는다.
  - 모든 요청에 구역 ID 모양의 `destination_id` 가 필요하다(`web/backend/app/main.py` 5번 검사, `orchestrator_node.py` `_on_deliver_goal`).
- 침대 구역 불일치:
  - **`pharmacy_only` 시연에는 영향이 없다.** 병동 구간을 실물 fleet 으로 돌릴 때만 부딪친다.
  - `zones.yaml` 의 침대는 `bed_a1` 하나다. 주문 풀의 `bed_a2`·`bed_b1`·`bed_b2` 는 없다([web API 9.1](../../web/api.md#91-알아-둘-불일치)).
  - 스텁 fleet 은 구역 ID 모양만 보고 받는다(`stub_fleet.py` `is_zone_id`). 실물 fleet 은 zones 에 없는 구역을 거부한다(`fleet_node.py`).

소요(실습8, sim s):

| 구간 | 값 |
| --- | --- |
| `REFILL_REQUESTED` → `REFILL_DONE` | 46.4-52.4 s(세 번) |
| `REFILL_DONE` → `DISPENSER_RESUMED` | 7.5-9.4 s |
| 한 바퀴(`REQUEST_ACCEPTED` → `DOCKED`, `pharmacy_only`) | 12.32-12.97 s(정상 배송 4회, 모두 긴급) |

- 한 바퀴는 보충과 겹쳐 진행된다. `REQUEST_ACCEPTED` 뒤 약 1 s 에 `DISPENSED`·`REFILL_REQUESTED` 가 나오고, 보충이 끝나기 전에 트립이 `DOCKED` 된다(master02, run `20260918T091837Z-master02-57682977`·`20260918T092036Z-master02-e618d1b1` 의 `events.jsonl`).

- 실습7-b 5분 연속(`refill_soak`, 오케스트레이터 없이)은 보충 7/7, 평균 46.37 s, 최대 50.68 s 였다.

## 3.5 2부 — 스텁 전 구간 한 사이클

1부(조제실 구간)와 **같은 기동에서 못 돌린다.** 스택 인자가 다르다. 1부를 내리고 2부를 띄운다.

- 보여 주는 것: 주문 하나가 조제 → 적재 → **병동 이동 → 환자 인증 → 보관함 수령** → 복귀까지 한 번에 도는 것.
- 주행·인증·수령은 **스텁**이다. Isaac 장면에는 병동이 없다.
- 범위: 1인 `ord-0001`(`bed_a1`) 한 건. **묶음은 하지 않는다.**
- 상태: **L3 3회 통과**(실습18·14p·19, `45d7fe3`). 세 회차 모두 창 모드 + 녹화이고 `HOLD_RETURN`·409·시한 걸림 0건이다.
  - 실습18: 세 트립이 전 구간을 돌고 주문 세 건이 `SUCCESS` 다(#240 issuecomment-5746910971).
  - 실습14p: 자동 긴급 14.73 s, 1인 15.17 s. `ord-0001` 은 `DELIVERED` 다(#240 issuecomment-5747476896).
  - 실습19: 자동 긴급 14.65 s, 1인 14.92 s. 병동 구간 3.43·3.47 s, 두 주문 모두 `DELIVERED` 다(#240 issuecomment-5748162014).
- 한 바퀴는 약 15 s 다(실습18 14.85 / 15.02 / 15.02 s, 실습14p 14.73 / 15.17 s). 그중 병동 구간(`DEPARTED` → `DOCKED`)이 3.3–3.7 s 다.

### 띄우기

```bash
tools/demo_v2.sh down        # 1부를 내린다. stage 까지 exit=0 을 본다
P3_STACK_CMD='source /opt/ros/jazzy/setup.bash && source '"$P3_REPO"'/install/setup.bash && export ROS_DOMAIN_ID='"$P3_DOMAIN"' && ros2 launch rokey_p3_bringup stub_loop.launch.py use_isaac_adapter:=true pharmacy_only:=false publish_clock:=false emulate_m0609:=false use_stub_m0609:=false dispenser_file:='"$P3_DISPENSER_FILE"' order_pool_file:='"$P3_REPO"'/src/rokey_p3_orchestrator/config/order_pool.yaml run_host:=master01' tools/demo_v2.sh up
```

- 바뀌는 것은 `pharmacy_only:=false` 하나다. 나머지 인자는 1부와 같다.
- **실렸는지 확인:** `tools/demo_v2.sh env` 는 `P3_STACK_CMD` 를 출력하지 않는다. 스택 로그의 `orchestrator up. … pharmacy_only=False` 줄로 본다.
- **전환은 약 100 s 다.** `down` 9.1 s, 2부 `up` 89.0 s 이고 대부분은 팔의 계획 캐시다.
  - `down` 을 친 때부터 첫 자동 요청까지가 실제로 기다리는 시간이다: 99.6 s(실습14p), 97.5 s(실습19).
  - 그 트립이 끝나는 데까지는 **약 115 s** 다(114.7 s / 112.3 s).
  - 그동안 발표자가 아래 ⓒ 문장을 말한다.

### 보일 장면

| 순서 | 무엇 | 화면에서 볼 곳 |
| --- | --- | --- |
| 1 | 자동 긴급 `ord-0002`(`bed_a2`)가 먼저 전 구간을 돈다 | 트립 칸의 `현재 단계` 글자가 이동 → 인증 → 수령 → 복귀로 바뀐다 |
| 2 | 웹에서 1인 `ord-0001`(`bed_a1`) 한 건. `DISPENSER_RESUMED` 뒤에 넣는다 | 주문 표의 `상태` 가 `DELIVERED` 로 끝난다(1부의 `HOLD_RETURN` 과 다르다). 한 바퀴 약 15 s |
| 3 | 리셋 | 1부와 같다 |

- **자동 긴급은 끌 수 없다.** `max_requests` 기본값이 1 이고, `0` 은 "끔"이 아니라 "주문 풀 전부"다(`stub_loop.launch.py` 인자 설명, `order_generator_node.py` `_tick`). 그래서 2부의 첫 장면은 언제나 `bed_a2` 행이다.
- 조제실 구간(벨트·팔·보충)은 1부와 똑같이 Isaac 화면에 보인다. 병동 구간만 웹 글자로 보인다.
- **`ARRIVING` 은 긴급 트립에만 나온다**(`trip_fsm.py:431` — 모드가 긴급이 아니면 내지 않는다. 트립당 한 번). 그래서 자동 긴급에는 보이고 1인에는 없다. 정상이다.
- 보충은 병동 구간과 겹쳐 돈다(실습18: 19.98 / 18.60 / 21.25 s). 그래도 1인은 `PAUSED` 가 사라진 뒤에 넣는다.

### 발표자가 말로 밝힐 것

**병동 구간은 약 3.6 s 만에 지나간다**(실습18). 이동·인증·수령이 순식간이라 발표자가 **그 순간에 말로 짚어야** 한다. 지나간 뒤에는 주문 행의 `DELIVERED` 표시가 남는다. 그것을 가리키며 아래를 말한다.

> 조제와 보충은 Isaac 안의 실물 팔이 합니다. 병동 이동과 환자 인증, 보관함 수령은 스텁입니다.
> 스텁 주행은 거리와 상관없이 1초에 도착하고, 구역 파일을 보지 않습니다. 그래서 구역 파일에 없는 침상에도 도착을 냅니다 — 지금 보시는 자동 주문의 `bed_a2` 가 그렇습니다.
> 병동은 이 화면에 없습니다. 그 구간은 오른쪽 웹 화면의 단계 글자로 보입니다.

### 하지 말 것

- **묶음을 넣지 않는다.** 전 구간 묶음은 L2·L3 모두 돌려 본 적이 없다.
- **실물 주행처럼 말하지 않는다.** 스텁이 도착을 내는 것이고, 실물 fleet 은 구역 파일에 없는 침상을 거부한다.
- 1부와 2부를 같은 기동에서 번갈아 돌리지 않는다.

### 2부가 안 뜨거나 멈추면

1. `tools/demo_v2.sh status` 로 어느 세션이 안 떴는지 본다.
2. `tools/demo_v2.sh down` 으로 내린다.
3. **1부 명령(인자 없이 `tools/demo_v2.sh up`)으로 돌아간다.** 1부는 오늘 여러 번 돌린 구성이다.
   - 다시 띄우면 창이 새로 뜬다. **브라우저 창이 화면에 보인 뒤에** `tools/demo_window_layout.py` 를 다시 부른다.
4. 2부는 다시 시도하지 않는다. 남은 시간은 1부 대본으로 채운다.

### STAT 터미널 데모 (본선과 별개, 1분)

본선과 연결하지 않는다(재범 결정 40). 노트북 한 대에서 터미널로만 돌린다.

- 사전 조건: ROS·Isaac·GPU·마스터·네트워크가 필요 없다. python3 3.10 이상이면 된다. 미리 `git fetch` 만 해 둔다.
- 브랜치 `feat/orchestrator-stat-s0-cli` 커밋 `8cd4023`(PR 없음)을 **별도 워크트리**로 꺼내 돌린다. 다른 사람이 쓰는 작업 트리에서 브랜치를 바꾸지 않는다. 임시 파일은 `mktemp -d` 폴더에만 생기고 저장소 안에는 아무것도 쓰지 않는다.

```bash
# 준비(발표 전에 미리)
git -C <저장소> worktree add --detach /tmp/stat-demo-tree 8cd4023
cd /tmp/stat-demo-tree/src/rokey_p3_orchestrator
export PYTHONPATH=$PWD
D=$(mktemp -d -t stat-demo-XXXX)
s0() { python3 -m rokey_p3_orchestrator.stat_cli --dir "$D" "$@"; }

s0 init && s0 demo && s0 run                 # (1) 정상 한 바퀴

D=$(mktemp -d -t stat-demo-XXXX); s0 init >/dev/null; s0 demo >/dev/null
s0 run --crash-at after_send:DISPENSE; echo "exit=$?"   # (2) 출고 직후 관제를 죽인다
s0 run                                                  # 새 프로세스가 복구한다

# 끝나고
rm -rf "$D"; git -C <저장소> worktree remove /tmp/stat-demo-tree
```

- 가리킬 곳과 말할 것:
  - `demo` 의 `first: ACCEPTED / STAT-0001` 과 `resend: REPLAY / STAT-0001` — "같은 요청을 다시 보내도 주문은 하나입니다. 같은 추적 번호를 돌려줍니다."
  - `run` 의 `DELIVERED`·`CLOSED` 와 `world_applied` 각 1회 — "인계 확정과 임무 종료를 따로 기록합니다."
  - crash 회차의 `exit=70` 뒤 재시작에서 `generation 2`·`DISPENSE 1` — "다시 켜도 재전송하지 않고 관측으로 대조합니다. **약이 두 번 나가지 않습니다.**"
- 걸리는 시간: 정상 한 바퀴 0.56 s, crash 회차 0.71 s. 사람이 치는 시간까지 합쳐 **1분 안**이다.
- **말로 밝힐 한계:** 전부 스텁이고 드론·로봇·Isaac 화면이 없다. 본선(조제·보충·주행·웹)과 연결돼 있지 않다. L3 미실행이고 계약은 proposed 다.
- **`master01`(Ubuntu 24.04, python 3.12.3)에서 확인했다**(9/20 11:1x). **발표에 쓸 기계가 다르면 그 기계에서 1회 더 돌린다.** 결과는: 기대값과 전부 같았다. `demo` 는 `first: ACCEPTED / STAT-0001`·`resend: REPLAY / STAT-0001`, `run` 은 `generation 1`·`DELIVERED`·`CLOSED`·장치 적용 각 1회. crash 회차는 `exit=70` 뒤 재시작에서 `generation 2`·`DELIVERED`·`DISPENSE 1`(출고는 여전히 한 번).
- 정리도 확인했다: 임시 폴더와 `/tmp` 워크트리가 지워지고 release 워크트리는 그대로다.
