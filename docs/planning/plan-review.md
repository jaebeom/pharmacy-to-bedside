병원 약제 물류는 주문·목적지·인계라는 경계가 있어서 통합 시나리오 후보로 적절하다.
다만 2주에 팔·AMR 2대·비전 학습·검수·동적 장애물·병동 하역·반복 평가를 한꺼번에 완성하는
계획은 통합과 계측에 쓸 시간을 잠식한다. **시나리오는 유지하고 최소 연결 사이클을 먼저
완성한 뒤 확장하는 방향**을 제안한다. 이는 아래 기술 자료와 원안의 작업 수를 바탕으로 한
프로젝트 판단이며 외부 기관이 보증한 일정은 아니다.

## 2. 기술 자료와 프로젝트 적용을 구분하기

### 2.1 다중 로봇은 예제에서 시작하되 부하까지 계측

**자료가 말하는 것:** NVIDIA의 Isaac Sim 5.1 다중 로봇 예제는 로봇별 namespace와 대응하는
launch 설정을 사용한다. 문서는 높은 CPU 사용량 때문에 센서 동기화·제어 명령에 문제가
생길 수 있음을 설명한다. [NVIDIA: Multiple Robot ROS2 Navigation](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/ros2_tutorials/tutorial_ros2_multi_navigation.html)

**우리 적용:** 예제를 복제해 첫 주행을 확인한 뒤 토픽·TF·명령 라우팅을 개별 검증한다.
두 마스터가 있으니 충분하다는 결론 대신 CPU/GPU·RTF·센서 주기·제어 지연으로 노드 배치를 정한다.
병원 씬을 여는 것과 두 AMR + 팔 + 카메라가 제때 동작하는 것은 다른 시험이다.

### 2.2 YOLO 출력과 파지 포즈 사이에 계약이 필요

**자료가 말하는 것:** Ultralytics 검출 결과는 bounding box·class·confidence이며, pose 작업의
일반 출력은 이미지 위 keypoint 좌표다. [Ultralytics: Object Detection](https://docs.ultralytics.com/tasks/detect/),
[Ultralytics: Pose Estimation](https://docs.ultralytics.com/tasks/pose/)

**우리 적용:** `검출 → 카메라 좌표 → 로봇 프레임 → 파지 가능 포즈`의 변환과 실패 조건을
따로 구현한다. 고정 평면·높이·yaw 제한을 사용하면 기록하고, 3D 포즈까지 학습했다고 표현하지 않는다.
처음부터 3종 물품·무작위 yaw·임의 적층을 풀기보다 위치만 바뀌는 1종 물품부터 연결한다.

### 2.3 AprilTag는 검사 수단이며 스스로의 정답이 아님

**자료가 말하는 것:** AprilTag 공식 구현은 태그 검출과 포즈 추정을 제공한다. 검출 거리와
처리속도 사이의 조정이 있으며, 포즈 추정에는 카메라 내부 파라미터와 태그 크기가 필요하다.
[AprilRobotics: AprilTag 3 — tuning and pose estimation](https://github.com/AprilRobotics/apriltag#tuning-the-detector-parameters)

**우리 적용:** 동일한 이미지에 같은 결과를 내는 구현이어도 실제 바구니의 모든 태그가
보인다는 보장은 없다. 읽힌 ID 목록을 정답으로 사용해 같은 목록의 정확도를 계산하면
미검출을 발견할 수 없다. 단층 배치/개별 검사로 관측 조건을 제한하고, 가려진 물품·잘못된
품목·누락/중복 태그를 주입한다. 평가기는 별도로 실제 물품 ID·도착 영역을 관측한다.
이 독립 경로 제안은 평가 설계 판단이며 AprilTag 문서가 제공하는 프로젝트 정답 장치가 아니다.

### 2.4 Surface Gripper와 물리 손가락 파지는 다른 모델

**자료가 말하는 것:** Isaac Sim 5.1 Surface Gripper 확장은 흡착 및 거리 기반 그리퍼 모델을
위한 기능이다. [NVIDIA: isaacsim.robot.surface_gripper](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/py/source/extensions/isaacsim.robot.surface_gripper/docs/index.html)

**우리 적용:** 빠른 통합 실험에 사용하는 것은 타당하다. 대신 모델 선택·부착 조건·파지한
물체·실패 조건을 기록한다. 이 결과를 Robotiq 손가락의 마찰 기반 파지나 실제 의료 물품
파지 성능으로 확대하지 않는다. 감점 여부는 강사 평가 해석을 확인하기 전 단정하지 않는다.

### 2.5 시뮬레이션 시간과 통신 감시 시간은 다름

**자료가 말하는 것:** ROS 시간 설계는 정지·역행을 지원하며, timeout 등에는 SteadyTime을
구분한다. Isaac Sim의 시계는 기본적으로 Stop/Play에도 계속 증가할 수 있고 `resetOnStop`
설정에 따라 달라진다. [ROS 2: Clock and Time](https://design.ros2.org/articles/clock_and_time.html),
[NVIDIA: ROS 2 Clock](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/ros2_tutorials/tutorial_ros2_clock.html)

**우리 적용:** `/sim/reset`이 모든 ROS 상태와 시계를 함께 초기화한다고 가정하지 않는다.
시계 설정과 새 epoch, 대기 중 action·예약·TF/인식 캐시·물리 초기 상태를 명시한다. `/clock`이
멈춰도 통신 두절 감시는 로컬 단조 시간으로 작동해야 한다. 실행 시간은 시뮬레이션 시간과
실제 경과 시간을 나란히 기록하고 서로 빼거나 합치지 않는다.

### 2.6 살아 있는 노드가 유효한 상태를 뜻하지 않음

**자료가 말하는 것:** ROS QoS 설계에서 deadline·liveliness·lifespan은 각각 데이터 주기,
생존성, 데이터 유효기간을 다룬다. Jazzy rclpy에는 deadline/liveliness 이벤트 콜백이 제공된다.
[ROS 2: QoS design](https://design.ros2.org/articles/qos_deadline_liveliness_lifespan.html),
[ROS 2 Jazzy: rclpy event handlers](https://docs.ros.org/en/ros2_packages/jazzy/api/rclpy/rclpy.event_handler.html)

**우리 적용:** 사용 RMW의 지원과 실제 동작을 확인하고 애플리케이션의 상태 유효성 검사도 둔다.
노드가 살아 있어도 이미지/TF가 오래됐거나 팔 상태가 불명일 수 있다. 중앙 허가 주체, 제어기
측 명령 만료, 관측 신선도와 epoch를 함께 검사한다. 예약 만료는 실제 점유 해제를 의미하지
않으므로 다른 AMR에게 곧바로 권한을 넘기지 않는다. 이 인터락 정책은 팀이 구현·시험할 설계다.

## 3. 20회 측정에서 주장할 수 있는 것

NIST는 작은 표본/적은 실패 수에서는 단순 정규 근사 구간이 부정확할 수 있으며 이항분포의
정확 구간을 설명한다. [NIST: Confidence intervals for proportions](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm),
[NIST: Exact binomial limits](https://itl.nist.gov/div898/software/dataplot/refman2/auxillar/exacbino.htm)

**방법을 적용한 계산 예시이며 실측이 아니다:** 독립적이고 동일 실패 확률인 20회에서 실패가
0회라고 가정해도, 실패 확률의 단측 95% 정확 상한은 `1 - 0.05^(1/20) ≈ 13.9%`다.
따라서 `20/20 성공`은 유용한 시연 실험 결과일 수 있으나 높은 신뢰도의 무고장 보증이 아니다.
같은 장면·seed의 반복 등으로 독립성/대표성이 약하면 그 가정과 한계를 함께 밝혀야 한다.

제안하는 절차는 다음과 같다.

1. pilot에서 계측과 재현을 확인한다. 발견한 문제와 후보 기준의 근거를 남긴다.
2. acceptance 전에 지표·분모·합격선·시나리오·seed·반복 수·타임아웃·중단 규칙을 고정한다.
3. 실행 후보의 코드·씬·모델·설정과 프로토콜 식별자를 실행 명세에 연결한다.
4. 실패·중단·타임아웃도 원래 실행 집합에 남긴다. 조건을 바꾸면 새 실험 집합으로 시작한다.
5. 수치 생성자와 다른 리뷰어가 원본에서 재집계하고, 그래프와 결론이 분모·범위를 지키는지 확인한다.

이는 [지표 정책](../policy/metrics.md)에 반영할 프로젝트 운영 규칙이다. 파일 해시는 저장 이후의
변경을 탐지하는 수단이며, 센서가 맞게 측정됐다는 보증이나 조작 불가능한 저장소 자체는 아니다.
원본 보존, 캘리브레이션, 별도 관측, 반복 검증과 리뷰를 함께 사용해야 한다.

## 4. 사업 가치와 현실 대응의 경계

병원별 이동 거리·주문량·배치·인계 방식·인력비·오류 비용을 아직 수집하지 않았으므로
ROI는 조사 가설이다. 노동 시간 감소를 바로 인원 감축액으로 계산하지 않고, 재배치 가능한
시간과 실제 절감액을 분리한다. 운영·감독·유지 비용을 포함한 순효과로 회수기간을 계산하며,
시뮬레이션의 오배송 판정 결과를 실제 투약 오류 감소율로 치환하지 않는다.

강사 원문은 출처 자료로 보존한다. 그 안의 물리 1:1, 지연 없는 연동, 현실에서도 거의 동일한
동작 같은 표현은 이번 프로젝트에서 검증한 성능 수치가 아니다. 외부 사실·수업의 기대·우리
실측을 구분하고, 구체적인 실물·데이터 연결과 보정이 없다면 검증된 디지털 트윈 범위를 제한한다.

## 5. 설계가 과해지지 않게 유지할 것

초기 설계에서 반드시 닫을 것은 파일 개수보다 **수정과 판단이 통과할 경계**다.

- 생산자·소비자가 합의할 프레임·시간·오류·허가 계약부터 만든다.
- 각 실행을 코드·조건·원본에 연결한다. 원본, 관측, 가설, 결정은 같은 문서의 사실처럼 섞지 않는다.
- 마스터 현장 에이전트는 배포·관측·재현에 집중하고 수정은 클라우드 PR로 검토한다.
- 작은 종단 실행이 새 가정을 검증하면 설계를 버전으로 개선한다. 모든 미래 요구를 미리 구현하지 않는다.
- 프레임워크/패키지/ADR는 실제 경계나 결정을 담을 때 만든다. 빈 모듈을 많이 만드는 것을 진척으로 세지 않는다.

팀이 먼저 채택할 결정은 G1 범위, 인계 모델, 그리퍼 모델, 평가 정답 경로, 계약 변경 방식이다.
이 문서와 기반 PR은 그 결정을 검토할 토대를 제공하며 시나리오 확정이나 현장 시험 완료를 대신하지 않는다.
